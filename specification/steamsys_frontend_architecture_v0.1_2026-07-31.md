# Фронтенд-архитектура steamsys.ru

## 0. Статус и назначение

Документ задаёт целевую фронтенд-архитектуру поэтапной модернизации steamsys.ru на существующей 1С‑Битрикс.

Он нужен для:

- единого понимания стека разработчиком, верстальщиком, дизайнером, QA и ИИ-агентами;
- оценки и реализации новых шаблонов без неоговорённой смены CMS;
- переиспользования UI-компонентов между волнами модернизации;
- сохранения SEO, контента и действующих функций во время поэтапного выпуска;
- определения границы между PHP-шаблонами, клиентским JavaScript, формами Битрикс24 и возможными сложными интерактивными модулями.

Статус `draft_for_technical_review` означает:

- архитектурные принципы являются рабочим предложением;
- фактические версии PHP, 1С‑Битрикс, Node.js, браузерная матрица, структура репозитория и release pipeline должны быть подтверждены разработчиком;
- документ нельзя считать основанием для смены CMS или создания собственного обработчика форм без отдельного согласования.

- конкретные дизайн-значения до утверждения актуального UI-kit;
- маркетинговая структура страниц, оффер, тексты, сценарии продаж и правила обработки лидов.

## 3. Основное архитектурное решение

steamsys.ru — контентный и коммерческий B2B-сайт инженерного интегратора с каталогом оборудования, системами, отраслевыми решениями, документацией, формами и инженерными инструментами.

```text
1С-Битрикс = основа
  CMS, URL, SEO, контент, инфоблоки, серверный HTML, права редакторов

PHP-шаблоны + SCSS = базовый интерфейс
  страницы, блоки, карточки, навигация и содержание

TypeScript/JavaScript = точечное улучшение
  меню, вкладки, фильтры, галереи, модальные окна, аналитика

Битрикс24 = внешняя система публичных форм и CRM
  формы создаются в Б24 и встраиваются на сайт предоставленными скриптами

TypeScript/JavaScript = единый клиентский слой
  включая калькуляторы, конфигураторы и другие интерактивные модули
```

### 3.1. Базовые принципы

1. Основное содержание и навигация рендерятся сервером.
2. Ключевой пользовательский путь не зависит от загрузки JavaScript, кроме функций, которые по своей природе требуют вычислений или динамического состояния.
3. JavaScript подключается только на страницах и для компонентов, где он нужен.
4. Новый интерфейс собирается из переиспользуемых компонентов и токенов.
5. Существующие инфоблоки и контент переиспользуются, если ревью не докажет необходимость локального расширения.
6. Новые и старые шаблоны могут временно сосуществовать во время поэтапного релиза.
7. Компонент не считается готовым без адаптива, клавиатурного управления и применимых состояний.
8. Прототипный HTML не переносится в production как самостоятельная архитектура или источник данных.

## 5. Базовый фронтенд-слой

### 5.1. Рабочий стек

| Технология | Назначение | Статус |
|---|---|---|
| PHP-шаблоны 1С‑Битрикс | Серверная разметка страниц и компонентов | Обязательно |
| HTML5 | Семантическая структура | Обязательно |
| SCSS | Организация стилей | Рабочее решение |
| CSS custom properties | Дизайн-токены и темы компонентов | Обязательно |
| BEM с проектным namespace | Именование классов базового слоя | Рабочее решение |
| TypeScript | Клиентский интерактив и аналитические адаптеры | Предпочтительно |
| Vanilla JavaScript | Допустим для небольших изолированных компонентов | Допустимо |
| Vite | Сборка SCSS, TS/JS, ассетов и manifest | Рабочее решение после проверки интеграции |
| SVG sprite / отдельные SVG | Иконки | Рабочее решение |

Фактические версии инструментов фиксируются после проверки окружения и политики обновлений. Значение `latest` в production-зависимостях запрещено.

### 5.2. CSS-архитектура

Рекомендуемая структура:

```text
src/styles/
├── tokens/
│   ├── _primitive.scss
│   ├── _semantic.scss
│   └── _component.scss
├── tools/
│   ├── _functions.scss
│   └── _mixins.scss
├── base/
│   ├── _reset.scss
│   ├── _fonts.scss
│   ├── _typography.scss
│   └── _global.scss
├── layout/
├── components/
├── pages/
├── vendors/
└── main.scss
```

Правила:

- селекторы компонентов не зависят от конкретного URL;
- вложенность SCSS ограничивается двумя уровнями, кроме состояний и media/container queries;
- цвет, типографика, отступы, радиусы, тени, motion и z-index берутся из токенов;
- допустимые исключения из токенов: вычисляемые значения, размеры реального медиа, технические поправки браузера; причина указывается рядом;
- `!important` допускается только для контролируемого vendor override или documented utility;
- стили встроенных форм Б24 изолируются в `vendors/bitrix24-forms` или отдельном адаптере;
- новые стили не должны глобально ломать действующие старые шаблоны.

### 5.3. Namespace

До реализации разработчик выбирает и фиксирует один namespace новых компонентов, например:

```scss
.ss-button {}
.ss-button__icon {}
.ss-button--primary {}
.is-open {}
```

Имена существующего сайта предварительно инвентаризируются. Namespace выбирается так, чтобы новые компоненты не конфликтовали со старым CSS и сторонними виджетами.

## 6. UI-система

### 6.1. Иерархия

```text
Примитивные токены
└── Семантические токены
    └── Токены компонентов
        └── Базовые элементы
            └── Составные компоненты
                └── Блоки страниц
                    └── Шаблоны 1С-Битрикс
```

### 6.2. Минимальный реестр первой волны

| Группа | Компоненты |
|---|---|
| Базовые | Button, TextLink, Icon, Badge, Input, Select, Checkbox, Radio, Textarea, FileInput |
| Навигация | Header, DesktopMenu, OverflowMenu, MobileDrawer, Breadcrumbs, LocalNav, Pagination |
| Контент | SectionHeader, RichText, Notice, ParameterTable, DocumentLink, Media |
| Карточки | SystemCard, ProductCard, CategoryCard, ArticleCard, CaseCard |
| Интерактив | Accordion, Tabs, Modal, Gallery, Filter, ShowMore |
| Коммерческие | CTA, B24FormContainer, ContactFallback, TrustBlock |
| Состояния | Skeleton при реальной необходимости, EmptyState, ErrorState, SuccessState |

Одинаковый визуальный элемент не создаётся заново для каждой страницы. Различия задаются вариантами компонента только тогда, когда подтверждены дизайном или функцией.

### 6.3. Контракт компонента

Для каждого переиспользуемого компонента фиксируются:

- назначение и места использования;
- входные данные;
- допустимые варианты;
- семантическая HTML-структура;
- desktop/tablet/mobile-поведение;
- default, hover, focus-visible, active/selected, disabled;
- loading, empty, success, error — если применимо;
- поведение без JavaScript;
- правила длинного текста, отсутствующего изображения и неполных данных;
- аналитическое событие, если действие является измеряемым;
- критерии визуальной и функциональной приёмки.

### 6.4. Витрина компонентов

Для ручной проверки создаётся одна служебная stage-страница UI-kit. На ней показываются переиспользуемые компоненты, варианты, состояния и контрольные примеры длинного или отсутствующего контента. Отдельный Storybook и сервис визуальной регрессии в базовый объём не входят.

## 7. Дизайн-токены

### 7.1. Три слоя

```text
primitive: фактические значения
semantic: назначение значения в интерфейсе
component: локальная настройка компонента
```

Пример:

```scss
:root {
  --ss-color-blue-700: #000000; // заменить утверждённым значением
  --ss-color-white: #ffffff;

  --ss-color-action-primary: var(--ss-color-blue-700);
  --ss-color-text-on-action: var(--ss-color-white);

  --ss-button-primary-bg: var(--ss-color-action-primary);
  --ss-button-primary-text: var(--ss-color-text-on-action);
}
```

До переноса значений из текущего `DESIGN.md` и `design-system/steamsys/MASTER.md` дизайнер и разработчик подтверждают актуальный источник правды. Значения из прототипов не становятся production-токенами автоматически.

### 7.2. Обязательные группы

- брендовые и нейтральные цвета;
- семантические цвета;
- типографика и межстрочные интервалы;
- spacing;
- размеры контейнеров и gutters;
- радиусы и границы;
- тени;
- z-index;
- длительности и easing;
- breakpoint/container rules;
- focus ring;
- минимальные touch-targets.

Тёмная тема не входит в базовый объём, пока не появится согласованный пользовательский сценарий и дизайн.

## 8. Клиентский интерактив

### 8.1. Принцип progressive enhancement

Базовое содержание, ссылки и основные действия доступны в серверном HTML. JavaScript улучшает интерфейс, но не используется для вывода критического SEO-контента с нуля.

Примеры:

- меню без JS сохраняет доступ к разделам через обычные ссылки;
- FAQ содержит вопросы и ответы в HTML;
- вкладки не удаляют содержание из исходного HTML;
- фильтр имеет согласованное серверное или URL-представление;
- карточка и её основная ссылка работают без обработчика клика;
- документ остаётся обычной ссылкой.

### 8.2. Реализация интерактива

Компоненты инициализируются по `data-*`-атрибутам и не зависят от уникального ID страницы:

```html
<div class="ss-tabs" data-component="tabs">...</div>
```

Каждый модуль:

- проверяет наличие корневого элемента;
- допускает несколько экземпляров на странице;
- не создаёт глобальное состояние без необходимости;
- корректно освобождает обработчики при повторной инициализации stage-preview, если это применимо;
- не падает из-за отсутствующих необязательных дочерних элементов;
- сохраняет нативную семантику и клавиатурное управление.

### 8.3. Единый клиентский стек

React и другие UI-фреймворки в проекте не используются. Весь клиентский интерактив реализуется на TypeScript/Vanilla JavaScript с нативными браузерными API.

Это относится в том числе к:

- инженерным калькуляторам;
- фильтрам и зависимым полям;
- многошаговым опросным листам;
- галереям, вкладкам, модальным окнам и навигации;
- передаче событий форм и аналитики.

Если отдельный будущий модуль невозможно разумно реализовать в утверждённом стеке, он не расширяет архитектуру сайта автоматически, а выносится в отдельный проект и отдельное решение владельца.

## 9. Формы Битрикс24

### 9.1. Архитектурная граница

```text
Сайт Steamsys
├── размещает предоставленный скрипт Б24
├── показывает форму в блоке или модальном окне
├── стилизует разрешённые элементы
├── передаёт поддерживаемый контекст страницы
├── обрабатывает доступные callbacks success/error
└── отправляет обезличенное аналитическое событие

Битрикс24
├── определяет поля и обязательность
├── валидирует и принимает данные
├── обрабатывает файлы и антиспам
├── создаёт CRM-сущность
└── выполняет маршрутизацию и уведомления
```

Собственный `/api/leads/`, локальное хранение заявок и дублирование серверной валидации не создаются.

### 9.2. Фронтенд-адаптер

Для форм создаётся единый адаптер, насколько это допускает API/скрипт Б24:

```ts
type FormContext = {
  formId: string;
  scenario: string;
  pageUrl: string;
  entityId?: string;
  entityName?: string;
};

type FormResult =
  | { status: 'success' }
  | { status: 'error'; reason: 'validation' | 'network' | 'service' | 'unknown' };
```

Точные callbacks и поддерживаемые скрытые поля заполняются после ревью каждой используемой формы.

### 9.3. Обязательное поведение

- submit-клик не считается успешной заявкой;
- success показывается только после подтверждения Б24;
- при недоступности формы показывается понятная ошибка и альтернативный контакт;
- ошибка не очищает введённые данные, если скрипт Б24 позволяет их сохранить;
- скрипт одной формы не загружается повторно;
- несколько форм не конфликтуют между собой, cookie-модулем, модальными окнами и аналитикой;
- персональные данные, комментарии и имена файлов не попадают в URL, аналитику и публичные логи;
- ограничения файлов показываются до отправки;
- фокус после открытия и закрытия модального окна возвращается корректно.

## 10. Аналитика

### 10.1. Основное решение

Базовый инструмент Steamsys — подтверждённый счётчик Яндекс.Метрики. GTM, GA4, Hotjar или другой инструмент не являются обязательной частью архитектуры без отдельного решения.

Код компонентов не вызывает `ym(...)` напрямую. Используется единый адаптер:

```ts
type AnalyticsPayload = Record<string, string | number | boolean | undefined>;

interface AnalyticsAdapter {
  track(event: string, payload?: AnalyticsPayload): void;
}
```

Адаптер:

- сопоставляет внутреннее имя события с целью Метрики;
- не передаёт персональные и технически чувствительные данные;
- защищается от повторной отправки события;
- безопасно ничего не делает, если счётчик недоступен;
- позволяет позже подключить подтверждённый дополнительный инструмент без переписывания компонентов.

### 10.2. Правила событий

- имя — стабильное, в `snake_case`;
- событие описывает подтверждённое действие, а не намерение;
- форма считается конверсией только после success Б24;
- ошибка формы и клик по submit — отдельные диагностические события;
- payload содержит только разрешённый контекст: тип страницы, ID/тип сущности, положение CTA, результат;
- имя, телефон, email, комментарий, параметры инженерной заявки и имя файла не передаются;
- карта событий ведётся отдельно и версионируется вместе с релизной волной.

## 11. UX-ошибки и состояния

| Сценарий | Поведение |
|---|---|
| JS не загрузился | Основной контент и обычные ссылки остаются доступны |
| Интерактивный компонент сломался | Страница продолжает работать; пользователь получает базовое действие или понятный fallback |
| Б24 недоступен | Ошибка без ложного success, повторная попытка и альтернативный контакт |
| Нет данных блока | Блок скрывается целиком вместе с заголовком, якорем, вкладкой и отступами |
| Нет результатов фильтра | Понятное empty-состояние, сброс фильтров и путь к консультации |
| Изображение отсутствует | Согласованная заглушка без сломанного layout |
| Документ отсутствует | Ссылка скрыта либо заменена согласованным запросом файла |
| Внешнее видео/карта недоступны | Остальная страница не ломается; показывается fallback |
| 404 | Корректный HTTP-статус, навигация и рабочие выходы |
| 500 | Без технических деталей; контакт и возможность повторить позже |

Сообщение об ошибке должно объяснять следующий шаг. Технические детали, stack trace и внутренние пути пользователю не показываются.

## 12. Доступность и адаптивность

Реализация ориентируется на WCAG 2.2 AA для ключевых сценариев без заявления о формальной сертификации.

Обязательно:

- семантические элементы и корректная структура заголовков;
- управление меню, dropdown, tabs, accordion, modal, gallery и filter с клавиатуры;
- видимый `focus-visible`;
- активная область ключевых touch-элементов не менее 44×44 px;
- программно связанные label и текстовые сообщения ошибок;
- контраст обычного текста не ниже 4.5:1;
- осмысленные alt или декоративная маркировка изображений;
- `prefers-reduced-motion`;
- отсутствие горизонтальной прокрутки всей страницы;
- таблицы и схемы могут прокручиваться внутри собственного контейнера;
- sticky-элементы не перекрывают контент, cookie-модуль и формы;
- интерфейс не зависит только от hover;
- порядок DOM остаётся логичным на всех ширинах.

Контрольные ширины и браузерная матрица берутся из функционального ТЗ и подтверждаются до оценки.

## 13. Производительность

### 13.1. Проектные цели

На согласованном тестовом профиле для ключевых шаблонов:

| Метрика | Цель |
|---|---:|
| LCP | ≤ 2,5 с |
| CLS | ≤ 0,1 |
| INP | ≤ 200 мс как рабочий ориентир до утверждения профиля |

### 13.2. Правила

- размеры изображений и медиа резервируются;
- изображения выдаются в подходящем размере и современном формате с fallback;
- медиа ниже первого экрана загружаются отложенно, если это не мешает индексации;
- главный LCP-ресурс не lazy-load;
- скрипты подключаются по необходимости, а не глобально;
- форма, карта, видео или аналитика не блокируют основной контент;
- сборка разделяет базовый код и тяжёлые модули;
- клиентский код остаётся модульным и не загружается на страницах без соответствующей функции;
- performance-budget для CSS и JS фиксируется после первого production-подобного шаблона;
- отчёт снимается минимум для главной, категории, карточки оборудования и страницы системы.

## 14. Сборка и доставка ассетов

### 14.1. Принцип

Предпочтителен один Vite pipeline для базового слоя. Второй конфиг или отдельная сборка добавляются только при появлении изолированного сложного приложения.

```text
src/
├── styles/
├── scripts/
├── components/
├── assets/
│   ├── icons/
│   ├── images/
│   └── fonts/

vite.config.ts
package.json
```

Сборка должна:

- выдавать хешированные production-файлы;
- формировать manifest для подключения из шаблона 1С‑Битрикс;
- не требовать Node.js на production во время HTTP-запроса;
- корректно работать на stage и production с разными базовыми путями;
- не коммитить случайные dev-сборки; порядок хранения production-сборки фиксируется разработчиком;
- обеспечивать детерминированную установку через lockfile.

### 14.2. Подключение в 1С‑Битрикс

Способ подключения manifest, CSS и JS подтверждает разработчик после проверки текущего шаблона. Нельзя:

- вручную прописывать хешированные имена файлов;
- подключать одинаковую библиотеку дважды;
- загружать код калькулятора, фильтра или галереи на страницах без компонента;
- заменять штатные механизмы Битрикса без зафиксированной причины.

## 15. Качество кода и ручная проверка

### 15.1. Локальные технические проверки

| Проверка | Способ |
|---|---|
| Форматирование | Prettier или согласованный formatter |
| TypeScript/JavaScript | ESLint |
| SCSS/CSS | Stylelint |
| Типы | `tsc --noEmit`, если используется TypeScript |
| Сборка | production build |
| Визуальные компоненты | Ручная проверка UI-kit на stage |
| Доступность | Ручная клавиатурная проверка и инспекция семантики |
| Производительность | Ручной замер Lighthouse/PageSpeed на ключевых шаблонах stage |

Линтеры и production build запускаются разработчиком локально перед передачей на проверку. CI/CD, unit-тесты, E2E-автоматизация и платные сервисы визуальной регрессии в базовый объём не входят.

### 15.2. Обязательный ручной чек-лист первой волны

- desktop и mobile-навигация;
- переходы по системам и каталогу;
- фильтрация и сброс фильтра;
- галерея карточки оборудования;
- локальная навигация и скрытие отсутствующих блоков;
- открытие, успешная и ошибочная отправка каждой формы Б24;
- передача контекста товара/страницы;
- одно аналитическое событие после подтверждённого success;
- отсутствие персональных данных в аналитике;
- 404, редиректы и ключевые SEO-теги;
- отсутствие горизонтального overflow на контрольных ширинах.

Результат фиксируется в релизном чек-листе: кто проверил, дата, окружение, устройства/браузеры, найденные дефекты и решение по ним. Прямые изменения production без ручной проверки stage и зафиксированного релизного контура запрещены.

## 17. Поэтапная модернизация

### 17.1. Сосуществование старого и нового

- каждый URL переключается только в составе согласованной волны;
- общие CSS/JS нового шаблона не должны ломать старые страницы;
- новые компоненты используют изолированный namespace;
- изменение данных проверяется на обратную совместимость со старым шаблоном;
- ссылки из новых страниц не ведут на локальные прототипы или несуществующие URL;
- до переключения подготовлены контент, формы, аналитика, SEO и откат;
- после переключения выполняется production-smoke.

### 17.2. Вертикальный срез

Каждый тип страницы проходит:

```text
постраничная спецификация
→ техническое сопоставление 1С-Битрикс
→ UI-компоненты и адаптивы
→ PHP-шаблон и клиентский интерактив
→ контент и формы
→ QA на stage
→ клиентская/SEO-приёмка
→ production и smoke
```

## 18. Правила для команды и ИИ-агентов

### 18.1. Блокирующие правила

1. Основной SEO-контент не создаётся только на клиенте.
2. React, другие UI-фреймворки и внешние state manager не используются.
3. Формы не получают собственный backend без изменения утверждённого ТЗ.
4. Успешная конверсия формы не отправляется до подтверждения Б24.
5. Персональные данные не передаются в аналитику, URL и публичные логи.
6. Компонент не принимается без адаптива и клавиатурного сценария.
7. Цвета, spacing, типографика, радиусы и z-index не хардкодятся вне токенов без документированной причины.
8. Прототипные заглушки, фиктивные success-состояния и `href="#"` не попадают в production.
9. Новый CSS и JS проверяются на старых страницах, остающихся в эксплуатации.
10. Линтинг, проверка типов и production build должны проходить локально; ручной релизный чек-лист должен быть заполнен.

### 18.2. Правила реализации

- сначала переиспользовать существующий компонент, затем расширять его и только потом создавать новый;
- не переносить текст или технические цифры из прототипа как подтверждённые данные;
- не придумывать источник автоматической подборки;
- не дублировать одну связь в нескольких инфоблоках;
- использовать обычные ссылки и нативные HTML-элементы;
- использовать делегирование событий только там, где оно упрощает динамический контент;
- защищать инициализацию компонентов от повторного запуска;
- именовать события по утверждённой карте;
- фиксировать нетривиальное архитектурное отклонение в журнале решений.
