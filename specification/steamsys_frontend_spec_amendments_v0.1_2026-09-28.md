# Предложения по правкам спецификации по вёрстке steamsys.ru

**Версия 0.1. Рабочий документ для обсуждения с Руководителем проекта.**

## 0. Назначение

Документ содержит предложения по уточнению `steamsys_frontend_spec_v0.3` и `steamsys_frontend_architecture_v0.1` в тех местах, где формулировки:

- задают избыточные требования, не поддержанные заявленным скоупом проекта;
- допускают неоднозначное толкование на приёмке;
- не разделяют «локальный конвейер каталога компонентов» и «production-сборка Битрикса»;
- могут быть усилены практикой изоляции, уже применяемой в репозитории редизайна.

Каждая правка сопровождается обоснованием и не меняет пользовательский сценарий, объём работ и договорные границы.

## 1. Границы предложения

Правки касаются только тех разделов, за которые отвечает верстальщик и клиентский JavaScript. Механика форм Битрикс24, серверные интеграции, инфоблоки, аналитический контур и релизный процесс не затрагиваются.

## 2. Предлагаемые правки

### 2.1. Токены: двухуровневая схема как рабочая, трёхуровневая — целевая

**Целевой раздел.** `steamsys_frontend_architecture_v0.1`, §7 «Дизайн-токены».

**Текущая формулировка.** Обязательные три слоя токенов: `primitive → semantic → component`.

**Предлагается.** Разрешить в качестве рабочего решения двухуровневую схему: `primitive + локальные компонентные переменные`. Semantic-слой вводится для группы токенов только тогда, когда ≥3 компонента ссылаются на один общий alias, либо появляется подтверждённый сценарий его использования (тема, брендинг, режим доступности).

**Обоснование.**

- Тот же документ прямо исключает тёмную тему из базового объёма (§7.2, последний абзац).
- Множественных брендов и режимов доступности в скоупе также нет.
- В отсутствие этих сценариев semantic-слой даёт удвоение имён без изменения поведения интерфейса.
- Двухуровневая схема сохраняет главное свойство архитектуры — точечную замену значения без правки компонентов, — потому что компоненты продолжают ссылаться через CSS custom properties.
- Правка не запрещает трёхуровневую схему, а делает её опциональной.

### 2.2. Vanilla JavaScript — основной клиентский стек

**Целевой раздел.** `steamsys_frontend_architecture_v0.1`, §5.1 «Рабочий стек».

**Текущая формулировка.** TypeScript — «Предпочтительно», Vanilla JavaScript — «Допустимо для небольших изолированных компонентов».

**Предлагается.** Зафиксировать Vanilla JavaScript как рабочий стек для базового клиентского слоя. TypeScript остаётся опцией для конкретного сложного модуля (инженерный калькулятор, конфигуратор, опросный лист с зависимыми полями).

**Обоснование.**

- Клиентский слой первой волны состоит из небольших изолированных компонентов: аккордеон, вкладки, дровер, инициализация слайдера, галерея, модальное окно. Все они попадают под уже разрешённую категорию Vanilla JS.
- Инженерные калькуляторы вынесены в Этап 4 дорожной карты и по факту оформляются как отдельные модули; их стек можно фиксировать отдельным решением по каждому калькулятору.
- Единый TS-конвейер по всему клиентскому слою даёт порог входа и время сборки, но не сокращает дефекты в слое, где основная сложность — DOM-события и `data-*`-атрибуты, а не бизнес-логика.
- Правка не запрещает TypeScript, а меняет default для базового слоя.

### 2.3. Явное правило корневой обёртки `.ss-wrapper`

**Целевой раздел.** `steamsys_frontend_spec_v0.3`, §5 «Компоненты и CSS» / `steamsys_frontend_architecture_v0.1`, §5.3 «Namespace».

**Текущая формулировка.** Требуется изолированный namespace классов и запрет глобальных стилей, ломающих старые страницы.

**Предлагается.** Добавить требование: все reset- и base-стили нового слоя ограничиваются корневым селектором `.ss-wrapper` (или эквивалентным контейнерным селектором), выбранным одним решением до начала реализации. Правило действует до окончания поэтапного релиза и полного вывода старой вёрстки.

**Обоснование.**

- Префикс `ss-` изолирует классы, но не защищает от селекторов по тегам. Правило вида `p { margin: 0; }` внутри `_base.scss` без корневого scope глобально ломает legacy-страницы, где новый CSS уже подключён.
- В условиях сосуществования нового и старого шаблонов на одном URL любой глобальный тег-селектор — источник трудно диагностируемых регрессий.
- Правило дешевле в поддержке, чем ручной аудит каждого нового `_base.scss`-правила на предмет протечки.

### 2.4. Двойное назначение UI-каталога

**Целевой раздел.** `steamsys_frontend_architecture_v0.1`, §6.4 «Витрина компонентов».

**Текущая формулировка.** «Одна служебная stage-страница UI-kit» для ручной проверки.

**Предлагается.** Признать за каталогом компонентов два назначения: stage-витрина для приёмки + справочная документация для backend/Bitrix-разработчика, интегрирующего компоненты в шаблон CMS.

**Обоснование.**

- Каталог естественным образом содержит семантическую HTML-структуру, варианты и состояния каждого компонента — тот же материал, который необходим разработчику CMS для переноса разметки в PHP-шаблон.
- Двойное назначение снимает вопрос о необходимости отдельного Storybook-подобного инструмента.
- Правка формализует уже сложившуюся практику и не добавляет объёма работ.

### 2.5. Уточнение требования 44×44 px

**Целевой раздел.** `steamsys_frontend_spec_v0.3`, §6 «Адаптивность» / `steamsys_frontend_architecture_v0.1`, §12 «Доступность и адаптивность».

**Текущая формулировка.** «Основные интерактивные области удобны для касания; целевой ориентир для ключевых элементов — не менее 44×44 px».

**Предлагается.** Уточнить: требование относится к интерактивной активной области (hit-area). Визуальный размер глифа или иконки может быть меньше при условии, что суммарная активная область с учётом padding’а не меньше 44×44 px.

**Обоснование.**

- В утверждённых макетах регулярно встречаются визуально небольшие иконки: закрытие модалки, стрелки слайдера, сортировка, «наверх». Их визуальный размер определяется дизайном и часто составляет 20–24 px.
- Стандартное a11y-решение — увеличить активную область через padding, не меняя визуальный размер. Формулировка «элемент не менее 44×44 px» допускает буквальное чтение и создаёт ложный дефект на приёмке.
- Правка приводит спецификацию в соответствие с WCAG 2.2 (2.5.8 Target Size — Minimum), где требование сформулировано именно к активной области.

### 2.6. Разделение локального конвейера и production-сборки

**Целевой раздел.** `steamsys_frontend_architecture_v0.1`, §14 «Сборка и доставка ассетов».

**Текущая формулировка.** «Предпочтителен один Vite pipeline для базового слоя».

**Предлагается.** Явно разделить два контекста:

1. **Локальный конвейер каталога компонентов и прототипов** — выбирается верстальщиком; не является production-сборкой и не подключается в шаблоны CMS напрямую.
2. **Production-сборка шаблона 1С-Битрикс** — выбирается разработчиком (Vite остаётся рекомендованным решением, как в текущей формулировке).

**Обоснование.**

- Локальный конвейер обеспечивает только сборку каталога `/ui/*.html` и прототипов страниц. Его артефакты передаются разработчику CMS как справочные шаблоны, а не как production-код.
- Production-подключение ассетов через manifest и хеширование, о котором говорит §14, целиком относится к CMS-стороне и уже помечено ответственностью разработчика.
- Действующий локальный pipeline (Gulp + Pug + SCSS) выполняет ровно ту роль, которую спецификация ожидает от stage-витрины. Смена на Vite на уровне каталога не даёт пользы, изменяющей приёмку.
- Правка не меняет производственный контур и не отменяет Vite для CMS-сборки.

### 2.7. Фиксация no-JS-контракта фильтра

**Целевой раздел.** `steamsys_frontend_spec_v0.3`, §8 «Клиентское поведение компонентов» / `steamsys_frontend_architecture_v0.1`, §8.1 «Принцип progressive enhancement».

**Текущая формулировка.** «Фильтр имеет согласованное серверное или URL-представление» и «Основной контент и обычные ссылки доступны без JavaScript».

**Предлагается.** Явно зафиксировать контракт fallback-разметки фильтра: обычный `<form method="GET">` с параметрами фильтра в query string. URL-состояние, требуемое для клиентского поведения (§8.1), совпадает с состоянием такой формы без JavaScript.

**Обоснование.**

- Без явного контракта не определено, какой уровень «работы без JS» ожидается от вёрстки фильтра до подключения к серверу.
- Формулировка через `<form method="GET">` совместима с любым серверным решением 1С-Битрикс, так как задаёт только транспорт параметров.
- Правка убирает риск ложного дефекта «фильтр не работает без JS» на этапе, когда серверная обработка ещё не подключена.

### 2.8. Префикс `data-ss-*` для атрибутов новых компонентов

**Целевой раздел.** `steamsys_frontend_architecture_v0.1`, §8.2 «Реализация интерактива».

**Текущая формулировка.** Пример инициализации: `data-component="tabs"`.

**Предлагается.** Использовать префикс `data-ss-*` для всех новых `data-*`-атрибутов слоя редизайна (`data-ss-component`, `data-ss-role`, `data-ss-options` и т. п.). Атрибут `data-component` без префикса допускается как исключение для совместимости с примером из спецификации.

**Обоснование.**

- В шаблонах 1С-Битрикс и legacy-разметке уже могут встречаться собственные `data-*`-атрибуты. Общий префикс изолирует новый слой на уровне атрибутов так же, как префикс классов `ss-` изолирует его на уровне CSS.
- Правка симметрична существующему namespace-решению и не требует дополнительных инструментов.

## 3. Что не пересматриваем

Требования спецификации, которые принимаются без изменений и уже применяются или планируются к применению:

- семантика HTML, корректная иерархия заголовков, осмысленный `alt`;
- состояния `default / hover / focus-visible / active-selected / disabled` на всех интерактивных элементах;
- клавиатурное управление меню, dropdown, вкладок, аккордеона, модалки, галереи и фильтра;
- `prefers-reduced-motion` для анимаций;
- контраст обычного текста ≥ 4.5:1;
- основная ссылка карточки — обычный `<a>`, а не JavaScript-обработчик;
- пустой блок скрывается целиком: заголовок, фон, якорь, пункт локальной навигации, отступы;
- максимум 6 карточек в каруселях и мини-подборках;
- отсутствие `href="#"` и прототипных заглушек в production;
- резервирование размеров или `aspect-ratio` у изображений; LCP-ресурс не получает `loading="lazy"`;
- «Показать ещё» без дублей;
- инициализация JS-компонента по корневому элементу с поддержкой нескольких экземпляров на странице.

## 4. Форма обсуждения

Правки предлагаются как поправки к следующей минорной версии соответствующих документов. По каждому пункту ожидается одно из решений владельца документа:

- принять формулировку;
- принять с уточнением;
- отклонить с обоснованием.

Отклонённые пункты фиксируются в журнале решений и не возвращаются к обсуждению без изменения контекста.
