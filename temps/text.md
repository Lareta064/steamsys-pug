● Нашёл причину. Это классический layout-shift баг. Восстанавливаю цепочку:

  1. Наводим на "…" → dropdown открылся.
  2. Наводим на "Услуги" (nested inline-аккордеон открывается — dropdown растёт).
  3. Наводим на следующий пункт — openItem синхронно закрывает Услуги, открывает новый nested. Высота dropdown прыгает.
  4. И так до последнего пункта с submenu (скажем, "Проекты"). Nested "Проекты" открыт.
  5. Наводим на "Контакты" (без submenu → без mouseenter listener'а). mouseleave предыдущего запустил scheduleClose(200 
  мс).
  6. Через 200 мс closeItem("Проекты") закрывает nested → dropdown "…" сжимается по высоте вниз.
  7. Курсор оставался на позиции, где раньше был "Контакты" — но сжатый dropdown уже не под курсором → браузер шлёт
  mouseleave на submenu "…" → scheduleClose("…") → ещё 200 мс → закрывает всё.

  Обходной путь пользователя («по краю») работает потому что nested не раскрываются, dropdown не растёт, курсор никогда
  не выпадает.

  Как чинить

  Правильное решение — не каскадно закрывать nested-items внутри "…" при переключении hover'а. Пусть остаются открытыми,
   пока весь dropdown "…" открыт. Тогда высота не прыгает, курсор не теряет dropdown.

  Одна правка в openItem: если и activeItem, и новый item находятся ВНУТРИ moreItem — не вызывать closeItem(activeItem).
   При выходе из "…" целиком closeItem("…") рекурсивно закрывает всё nested (эта логика уже есть).

  Trade-off: если пользователь долго бродит внутри "…", несколько nested-аккордеонов останутся открытыми одновременно.
  По UX — нормально: пользователь видит контекст, где был; при выходе всё схлопывается разом.
